# EMA Crossover: Pine Script -> async Python

Перенос стратегии `EMA Crossover` (Pine Script v5, TradingView) на асинхронный Python
с бэктестом на минутных свечах Bybit Spot (BTCUSDT, последние 1000 свечей).

## Запуск

Python 3.11+.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python solution.py
```

Тесты:

```bash
pip install -r requirements-dev.txt
pytest -q --cov=solution
```

Скрипт выводит в консоль:
1. сводку по очистке данных (дубли, битые бары, незакрытая свеча, пропуски);
2. предупреждения о проскальзывании > 0.5%;
3. список закрытых сделок: время и цена входа/выхода, чистый PnL в % и USDT, отметки;
4. итог: число сделок, winrate, суммарный чистый PnL.

## Как устроено

Всё в одном скрипте `solution.py`, по секциям:

| Секция | Что делает |
|---|---|
| Data fetching | Один асинхронный запрос `GET /v5/market/kline` через `httpx`, повтор с экспоненциальной задержкой на 429/5xx/сетевые ошибки, проверка `retCode` |
| Data cleaning | Разбор, удаление дублей, незакрытой и битых свечей, сортировка, подсчёт пропусков |
| Indicators | `ta.ema`, `ta.crossover`, `ta.crossunder` на numpy без TA-библиотек |
| Backtest | Long-only: сигнал по Close бара T, исполнение по Open бара T+1, комиссии, проскальзывание, принудительное закрытие |
| Console report | Форматирование вывода |

### Очистка данных

* **Обратный порядок.** Bybit отдаёт свечи от новых к старым, сортируем по возрастанию.
* **Битые бары:** цена <= 0, `high < low`, open/close вне диапазона `[low, high]`, время не кратно минуте, нечисловые поля. Удаляются до поиска дублей, чтобы битая копия минуты не вытеснила нормальную.
* **Дубли** по времени открытия: оставляем первое вхождение. Копии закрытой минуты в одном ответе должны совпадать; если нет, надёжного критерия выбора нет, поэтому сохраняем порядок ответа.
* **Незакрытая свеча.** Бар, у которого `start + 1 мин > server time` из ответа Bybit, отбрасывается: его Close ещё не финальный, сигнал на нём перерисовывался бы.
* **Пропуски минут** считаются, но не заполняются: TradingView не рисует бары для минут без сделок, синтетические бары увели бы EMA от графика. Исполнение идёт по Open следующего реального бара.

### Индикаторы

* `ta.ema`: `alpha = 2 / (length + 1)`, первые `length - 1` значений `na`, первое значение - SMA первых `length` свечей, далее `ema = alpha * src + (1 - alpha) * ema[1]`.
  `pandas.ewm(adjust=False)` не подходит: он стартует с первого значения без `na`-разгона, и ранние пересечения сдвигаются.
* `ta.crossover(a, b)`: `a > b` и `a[1] <= b[1]`; `ta.crossunder(a, b)`: `a < b` и `a[1] >= b[1]`. Сравнение с `na` ложно, поэтому в период разгона сигналов нет.

### Исполнение и PnL

* Только покупка: вход по `buySignal`, выход в кэш по `sellSignal`. Повторный buy в позиции и sell без позиции игнорируются.
* Сигнал известен только после закрытия бара T, сделка исполняется по Open бара T+1: look-ahead исключён.
* Сигнал на последнем баре не исполняется (нет следующего Open) и выводится отдельной строкой.
* Позиция, открытая на конец данных, закрывается по последнему Close с отметкой `forced close`.
* **Размер и комиссии.** Вход на 1000 USDT, покупается `1000 / entry_price` монет. Комиссия 0.1% берётся сверху от суммы входа, 0.18% - от фактической суммы выхода `qty * exit_price`.
  `PnL = qty * exit - 1000 - 1000 * 0.001 - qty * exit * 0.0018`, PnL % считается от 1000 USDT.
* **Проскальзывание** - отклонение цены исполнения от Close сигнального бара. Если оно больше 0.5% по модулю, выводится `WARNING` и сделка помечается `SLIPPAGE`.

## Расхождения с TradingView

Где сигналы могут отличаться от графика и почему:

1. **Разгон EMA.** TradingView считает EMA по всей истории графика, а у нас только 1000 свечей, и EMA стартует с SMA на 21-й свече. Ошибка старта затухает как `(1 - alpha)^n`: для EMA(21) через 100 баров это около `7e-5` от начальной разницы. После первых ~100 свечей значения практически совпадают с графиком, а сигналы в начале выборки, где EMA ещё разгоняется, могут отличаться или отсутствовать.
   Скрипт считает эту границу сам (`warmup_bars`: бар, после которого вес стартового SMA падает ниже 0.1%, для EMA(21) это 93-й бар) и помечает такие сделки в отчёте как `EMA warm-up`.
2. **Почти равные EMA.** Когда быстрая и медленная EMA расходятся на сотые доли, пересечение зависит от последних знаков цены. Если поток TradingView для `BYBIT:BTCUSDT` отличается от REST API хотя бы на один тик, такой сигнал может сдвинуться на бар.
3. **Текущая свеча.** На графике сигнал на незакрытой свече появляется и пропадает в реальном времени. Мы её отбрасываем, поэтому самый свежий живой сигнал TradingView в отчёт не попадёт.
4. **Пропуски.** Если у Bybit нет бара за минуту, график TradingView его тоже не рисует, поэтому EMA считаются одинаково. Различие возможно, только если у TradingView есть бар, которого нет в ответе REST.
5. **Время.** Всё выводится в UTC. На графике TradingView нужно выставить тот же часовой пояс, иначе время сигналов кажется сдвинутым.

Для сверки: откройте `BYBIT:BTCUSDT` на таймфрейме 1m, добавьте исходный Pine-скрипт, часовой пояс UTC, и сравните время сделок (сигнальный бар = время входа минус 1 минута).
